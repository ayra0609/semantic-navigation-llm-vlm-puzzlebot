# 2026-06-24

## Real Robot Debugging - PuzzleBot Encoder Feedback, Collision Status, and UI Safety Messages

Today focused on debugging the real PuzzleBot deployment after repeated tests with natural
language navigation commands such as:

```text
go to the Box
go to the Chair
go to the Bag
```

The main goal was to make the real robot pipeline safer and easier to interpret from the UI:

```text
Natural-language command
-> LLM intent extraction
-> Grounding DINO + Depth Anything perception
-> ROS2 navigation control
-> PuzzleBot UDP wheel commands and encoder feedback
-> UI natural-language status
```

---

## 1. LLM Intent Parsing Fix

### Symptom

The UI returned:

```text
Could not parse "go to the Box"
```

### Root Cause

The LLM/regex intent extraction path was too sensitive to surface wording and capitalisation.
Commands such as `go to the Box` were not always normalised into the expected navigation
intent.

### Fix - `llm/intent_extraction.py`

Added a normalisation layer for navigation actions and targets so that commands such as
`go to the Box` are converted into:

```python
{"action": "navigate_to", "target": "box"}
```

The fix reduces UI-level command rejection for simple natural-language navigation requests.

## 2. PuzzleBot Encoder Feedback and Odom Integration

### Symptom

The Jetson could ping the PuzzleBot at `192.168.1.1`, and `/cmd_vel` commands were being sent,
but the old odometry path did not receive encoder feedback:

```text
enc_age=infs fresh=False
```

Initial UDP sniffing showed no parseable packets on the expected listener path, but `tcpdump`
later showed that the PuzzleBot sent UDP feedback back to the ephemeral port used by the
command socket:

```text
192.168.1.1:3142 -> 192.168.1.2:<ephemeral-port>
```

### Root Cause

The old architecture separated command output and odometry input. In practice, the PuzzleBot
returns `VelocityEncR/L` feedback to the same UDP socket that sends `VelocitySetR/L`.
Therefore `cmd_vel_bridge.py` needed to receive and parse encoder packets directly.

### Fix - `ros2/cmd_vel_bridge.py`

Extended the bridge from a one-way `/cmd_vel -> UDP` sender into a bidirectional bridge:

- Sends `VelocitySetR` and `VelocitySetL` to the PuzzleBot.
- Receives `VelocityEncR` and `VelocityEncL` feedback on the same UDP socket.
- Publishes `/odom` from wheel encoder feedback.
- Publishes TF from `odom` to `base_link`.
- Marks odometry freshness in covariance:
  - `pose.covariance[0] >= 0`: encoder feedback fresh
  - `pose.covariance[0] < 0`: encoder feedback stale
- Resends the latest command at 20 Hz while the command is fresh.
- Sends a zero-velocity stale stop after `/cmd_vel` input stops.

Manual testing confirmed that odometry became fresh and pose changed after motion commands:

```text
[ODOM] x=0.051 ... enc_age=0.02s fresh=True
```

## 4. Collision / Stuck Detection Added and Iteratively Tuned

### Initial Requirement

When the physical robot bumps into a chair leg or becomes stuck, the UI should return a
clear natural-language safety message within a reasonable time window:

```text
I may have bumped into something or got stuck, so I stopped.
```

### Implemented Detection Signals - `ros2/navigation_node.py`

Added several safety checks:

| Signal | Purpose |
|---|---|
| Odom stale while commanding motion | Detect missing wheel feedback during movement |
| No visual progress | Detect when target distance/area does not improve |
| Edge-stuck heuristic | Detect when target remains near image edge during motion |
| Perception risk score | Use Grounding DINO + depth cues as a lightweight visual collision-risk head |

The perception risk head does not introduce a new downloaded neural network. It uses existing
pretrained perception outputs:

```text
Grounding DINO bounding box + Depth Anything distance
-> edge score, close score, area score, bottom-of-frame score
-> collision/stuck risk estimate
```

### Important Real-World Limitation

Wheel encoders can continue rotating even when the robot body is physically blocked. This
means encoder odometry alone cannot reliably detect every real collision. Visual progress
and target-position cues are needed as an additional safety layer.

## 5. UI Collision Text Mapping Bug Fixed

### Symptom

After a collision, the UI still displayed:

```text
I can see the target. I am moving closer.
```

even though the backend log contained:

```text
ERROR: Collision detected -- wheel encoder feedback stopped while moving
```

### Root Cause

The UI status formatter matched the generic substring `detected` before checking specific
error types. Therefore:

```text
ERROR: Collision detected ...
```

was incorrectly mapped to the target-detection message.

### Fix - `web_ui/index.html`

Moved all `ERROR:` handling above generic target-detection handling. Collision statuses now
map correctly to:

```text
I may have bumped into something or got stuck, so I stopped.
```

## 6. Encoder Feedback Loss Separated from Collision

### Symptom

In an obstacle-free test, the UI showed the collision message even though the robot had moved
normally and then stopped.

### Root Cause

Short-term encoder feedback gaps or stale odometry were being treated as collision. This was
too aggressive for Wi-Fi/UDP communication and could confuse communication loss with a real
physical bump.

### Fixes

#### `ros2/cmd_vel_bridge.py`

Added a separate encoder-loss timeout:

```python
ENCODER_LOST_STOP_S = 3.0
```

Encoder feedback loss is no longer reported as collision. It now publishes:

```text
ERROR: Encoder feedback lost -- wheel encoder feedback stopped while moving
```

#### `ros2/navigation_node.py`

Increased stale-odom tolerance:

```python
ODOM_STALE_MOTION_STOP_S = 3.0
```

Added a separate stop reason:

```text
encoder_lost
```

#### `web_ui/index.html`

Added a separate UI message:

```text
I lost wheel feedback, so I stopped for safety.
```

#### `ros2/pipeline_node.py`

Updated trial-ending logic so `ERROR: Encoder feedback lost` is treated as a completed
navigation trial and metrics are logged.

## 7. False Positive on `go to the Bag` Fixed

### Symptom

During a `go to the Bag` test, the UI returned:

```text
I may have bumped into something or got stuck, so I stopped.
```

even though the robot was still making progress toward the target.

### Log Evidence

The trigger was `NO_PROGRESS`:

```text
[NO_PROGRESS] elapsed=8.5s dist 1.60->1.17m area 0.08->0.15 cmd_lin=0.10
```

This was a false positive. The distance decreased from `1.60 m` to `1.17 m`, and the bounding
box area increased from `0.08` to `0.15`, so the robot was approaching the bag.

### Root Cause

The progress threshold was too strict:

```python
NO_PROGRESS_MIN_DIST_DROP_M = 0.45
```

The actual distance reduction was about `0.43 m`, which was physically meaningful but just
below the threshold.

### Fix - `ros2/navigation_node.py`

Relaxed the no-progress detector:

```python
NO_PROGRESS_TIMEOUT_S = 10.0
NO_PROGRESS_MIN_DIST_DROP_M = 0.20
NO_PROGRESS_MIN_AREA_GAIN = 0.04
```

This should prevent soft objects such as bags from being incorrectly classified as stuck
when the detected distance and bounding-box area are improving.

## 8. NCC / VLM Unavailable Handling

### Symptom

During NCC startup or temporary server failure, navigation could continue with missing
detection data.

### Fixes - `ros2/pipeline_node.py` and `ros2/navigation_node.py`

When NCC inference fails, the pipeline now publishes a structured unavailable result:

```python
{
    "found": False,
    "target": target,
    "ncc_unavailable": True,
    "vlm_unavailable": True,
    "error": str(e),
}
```

The navigation node now holds still while NCC is unavailable and reports a failure if the
unavailable state persists:

```python
NCC_UNAVAILABLE_TIMEOUT_S = 15.0
```
