## Problem 1: Robot Collided with Target at Arrival

### Symptom
Trial at 22:54 (`202605192252.log`): the robot successfully located and approached "the white
stool" but physically bumped into the chair leg. The system still reported
"Target reached. I have arrived at the destination."

### Root Cause
The arrival stop relied on dead-reckoning (DR) integration:
`covered_distance >= total_estimated_distance - ARRIVE_THRESHOLD (0.25 m)`

Depth Anything V2 distance estimates were noisy at close range — the same stool registered as
2.32 m, then 2.95 m, then back to 1.64 m within a few seconds. This inflated the DR
`_dr_dist` total, so the stop triggered later than expected. The bounding-box area fallback
(stop at 40% image coverage) also failed because the thin chair legs never filled enough of
the frame.

From the log (dist readings during final approach):
```
2.32m → 2.41m → 2.95m → 2.95m → 1.64m → 1.45m → 1.08m → 0.93m → 0.75m → [collision]
```

### Fix — `ros2/navigation_node.py`

Added a direct depth-based stop that bypasses DR integration entirely.

**New parameter:**
```python
DIST_STOP_DISTANCE = 0.30   # stop immediately when live depth reading <= this
```

**`detection_callback`**: when any incoming detection has `dist_m <= 0.30 m` and
`score >= 0.50`, set `self._dist_arrived = True` immediately.

**`_control_loop_impl`**: check `_dist_arrived` at the top of every 100 ms tick; if set,
call `stop_robot('arrived')` before any other motion logic executes.

**`stop_robot`**: reset `_dist_arrived = False` on each new navigation goal.

This guarantees the robot halts within one control cycle (≤ 100 ms) of the depth sensor
reading ≤ 0.30 m, regardless of DR state.

## Problem 2: Alignment Stall — Stale Detection Holds Wrong Heading

### Symptom
During approach, the robot entered ALIGNING mode with `error = +251 px` and continued
sending the same corrective command for ~4 seconds without the error changing. The robot was
physically turning, but the heading error appeared frozen.

From the log (excerpt):
```
[CMD_VEL] ALIGNING  error=+251px  ang=-0.126   (repeated ~40 consecutive ticks)
[CMD_VEL] ALIGNING  error=+264px  ang=-0.132   (new detection, still off-centre)
```

### Root Cause
Grounding DINO runs at ~0.5 Hz (one inference every ~1.6–1.9 s on NCC), while the ROS2
control loop runs at 10 Hz. The `DETECTION_TIMEOUT = 4.0 s` hysteresis holds the last
positive detection for up to 4 seconds to prevent a single missed frame from triggering a
full search rotation. During that window the robot turns based on an already-outdated heading
error, overshoots, then waits for the next DINO frame to correct — causing visible
oscillation.

### Mitigation (already applied before today)
- PID gain reduced from `Kp = 0.003` to `Kp = 0.001`, limiting angular correction to
  ≤ 0.18 rad per DINO interval (previously 0.54 rad, enough to overshoot by 31°).
- Robot moves forward at half speed (0.075 m/s) while aligning rather than rotating in
  place, so it makes spatial progress even during oscillation phases.
- System eventually converges as successive frames close the error:
  `+251 px → +264 px → +81 px → −110 px → −214 px → −169 px → centred`

**Remaining limitation:** with 0.5 Hz detection, initial alignment for targets > 200 px
off-centre can take 6–10 s. Increasing NCC throughput or adding optical-flow tracking
between DINO frames would reduce this.

inflated depth reading. The new `DIST_STOP_DISTANCE = 0.30 m` guard provides an additional
safety layer for future trials.
